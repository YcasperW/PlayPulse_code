# 04 · 决策记录

> 换设备、换人接手、或者三个月后回来看时，**先读这个文件**。
> 记录每个关键决策的「结论 + 理由 + 当时的替代方案」，避免重复论证。

---

## D1 · 不做通用 Text-to-SQL（2026-09-18 · 已定）

**结论**：LLM 不生成 SQL。指标预定义为「分析卡片」，LLM 只负责选卡片、填参数、解读结论。

**理由**：
1. 指标本体是预定义的，绝大多数分析可以落成参数化查询，不需要自由生成。
2. 更准（不会生成错 SQL）、更快、更可控（可审计、可回放）。
3. 彻底避开 SQLBot 的主场——在别人的强项上比拼没有胜算。

**风险**：灵活度下降，遇到预定义之外的分析需求时无能为力。
**缓解**：问答兜底时允许「建议新增指标」，把长尾需求转成配置沉淀，而不是临时生成 SQL。

## D2 · 定位为「工作室级跨项目基准线」，不是「通用游戏 BI」（2026-09-18 · 已定）

**结论**：主打跨项目 Benchmark（PlayBench），而不是通用性。

**理由**：
- 「一个工具能给 20 个项目用」只是复用，评审会问「那他们为什么不用 Excel」。
- 「20+ 项目数据放一起，能回答工作室层面从来没人回答过的问题」——这才是别人做不到的。
- 且自带飞轮：接入越多 → 基准越准 → 对每个项目越有价值 → 越容易推动下一个接入。

**代价**：定位要诚实收窄。若 20+ 项目都是休闲品类，就只能说「休闲游戏测试分析」，不能吹通用。

**2026-09-24 已落地**：`playpulse/bench.py` + `python -m playpulse bench ...`，规矩是
**一项目一票、只比通用层、项目数不到 3 个不给基准线**。详见 `07-PlayBench-跨项目基准线.md`。

## D3 · 定名 PlayPulse · 把脉（2026-09-18 · 已定）

**结论**：`PlayPulse`，中文「把脉」；模块名 Pulse Check / PlayBench / Signal-Noise。

**理由**：
- 中文名能当动词用：「给游戏把个脉」——立项现场一句话说清，比 PPT 好使。
- 意象是「主动体检 + 出诊断」，正好对应「不等提问先出报告」这个核心差异化。
- 不锁死品类与阶段（以后接留存/付费/线上数据也说得通）。
- GitHub 可搜、不与知名项目撞车。

**否决的候选**：
- `Playtest Copilot` —— Copilot/GPT 后缀在 2026 年 = 套壳暗示。
- `Stetho` —— 与 Facebook 的 Android 调试库重名。
- `DifficultyLens` / `LevelScope` —— 锁死在「难度 / 关卡」，后续扩展讲不通。
- `PlayBench` —— 更直击基准线，但听起来像纯基准工具，弱化诊断报告；降级为模块名保留。

## D4 · MVP 只做三件事（2026-09-18 · 已定）

**结论**：① CSV 规范化入库 ② 难度体检报告 ③ 版本对比 Diff。

**明确不做**：通用问数、图表美化、仪表板、预测功能。

**2026-09-24**：三件事都已完成（代码 4032 行 / 105 个 def），并补上 V1 的两块：
PlayBench 跨项目基准线、Streamlit 多页版。

**理由**：
- 最大风险是项目退化成「SQLBot 简化版」，一旦发生就废了。
- 在小样本上做预测，和「小样本诚实性」这个卖点自相矛盾。
- 三个功能足以证明「报告先行 + 语义层 + 版本对比」这三个差异化。

## D5 · 不重复 SQLBot（2026-09-18 · 已核实）

**事实**（2026-09 核查）：SQLBot 由 dataease 出品，2025-08 发布，3000+ star / 12 万+ 部署，
Text-to-SQL + RAG + 图表 + 多轮对话 + 术语库校准 + 嵌入式 MCP 全都有，GPL 协议免费商用受限。

**结论**：这条赛道已走完，重复造零价值。差异化必须建立在 SQLBot 的结构性盲区上——
**它假设用户知道自己该问什么，而策划不知道。**

**Quick BI 智能小Q 的信号**：已从「问答」进化到「数据获取 → 分析结论 → 策略输出 → 报告撰写」，
核心卖点是波动归因、异常自动下钻、计算过程可验证。→ 行业共识：**问数本身已不是价值，从数据到决策才是。**

## D6 · 未上线阶段不测留存（2026-09-18 · 已定）

**结论**：内部试玩阶段，留存 / 付费率 / eCPM / LTV / 掉率精确性**全部不测**，改用三个代理指标。

**理由**：同事是「给面子玩」，不会真流失。测出来的留存会虚高到毫无意义，只会误导决策。

**代理指标**：无激励额外游玩时长 / 次日自发回归 / 自然停止点。详见 `02-数据采集方案-内部试玩.md`。

---

## D7 · 采集表量化优先（2026-09-18 · 已定）

**结论**：能编码的绝不自由填。10 份问卷的开放题做不出任何统计结论，所以每个定性判断都必须配一个数字字段。

**四个具体改造**：
1. **绝对分 → 相对增量**：1–7 分锚点因人而异，改问「比上一关难多少」−2~+2，跨人可比且能累加成感知难度曲线。
2. **加行为数字层**：APM、无效操作率、最长停顿、停顿>5s 次数、跳过动画次数、**切屏/看手机次数**（最强厌倦信号）。这些不用问，回看录屏数就行。
3. **强制选择代替意愿提问**：不问「你愿意付费吗」，问「卡住了只能选一个：等 / 看广告 / 花 6 元 / 退出」。
4. **感知掉率**：让玩家填估计概率，与配置值对比得感知偏差。

**配套决策**：采集表拆成「现场填写表」+「录屏回看编码表」两张。
理由：现场根本数不清 APM 和停顿次数，硬填只会得到假数据；录屏本来就要录，行为数字统一事后补。

**编码表必须提前定**：事后看着答案编编码 = 先射箭后画靶。
