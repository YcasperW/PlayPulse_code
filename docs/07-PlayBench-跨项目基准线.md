# 07 · PlayBench 跨项目基准线

> 模块②。单个项目只能回答「我这游戏第几关最难」，
> 回答不了「同类项目一般第几关最难」——后者才是这个模块存在的理由（决策 D2）。

---

## 1. 一句话

把每个项目每次体检的结果攒下来，攒够项目数，就能说清你这一个项目在同类里排什么位置。

---

## 2. 三条规矩

| 规矩 | 具体是什么 | 为什么 |
|---|---|---|
| **一个项目一票** | 算基准线时每个项目只取最近一次体检 | 否则「测了很多次的项目」会把基准线拽向自己，那不是基准，是被刷的榜 |
| **只比通用层指标** | 只认 `layer: universal` 的指标 | 开箱数和回合数没法放一起比。这条反过来解释了为什么通用层口径必须强制统一 |
| **项目数不到 3 个不给基准线** | `MIN_PROJECTS = 3` | 1 个是孤例，2 个是两点一线，都不是分布。跟小样本拒绝下结论是同一套逻辑 |

第三条是硬规矩，不是提示。项目数不够时，界面和报告都会直接说「攒不够」，
不会给你一个「你高于行业平均」的漂亮数字。

---

## 3. 存什么、不存什么

```
data/bench/<项目名>/<时间戳>.json
```

一个项目一个目录，目录就是隔离边界（立项前提 Q4）。

存进去的：

- 通用层指标的点估计（每关一个数）
- 难度曲线形状与最大跳变比
- 触发了哪些规则、严重度、当时的取值
- 玩家数、关卡数、版本号、是否合成数据、备注

**不存的**：任何一行原始数据。

原始行留在项目组自己手上。基准线要的是「这个项目这关大概多少」，
不需要知道每个玩家点了几下。这样也顺手解决了未上线项目的数据敏感问题——
项目之间只共享数字，不共享数据。

---

## 4. 基准线怎么算

1. 每个项目取最近一条记录
2. 按（指标 × 关卡序号）摊平对齐——第 2 关跟第 2 关比，不跟「倒数第二关」比
3. 每一格单独算 P10 / P25 / P50 / P75 / P90 / 极值
4. 每一格的样本量（n_projects）单独报，因为各项目关卡数不一样

P25–P75 就是「同类的正常区间」。落在这个区间里，说明你这关没什么特别的。

---

## 5. 判定规则（这块踩过坑）

第一版直接用「> P75 就算高于同类」，结果 3 个项目时几乎全部命中——
因为项目少的时候分位数会退化成一坨相同的值（`p25 == p50 == p75`），
只要比中位数高 0.1 就被判成「高于 P75」，39 行里 30 行报警，等于没说。

现在的判定：

| 情况 | 怎么判 | 显示成什么 |
|---|---|---|
| 各项目取值完全一样（`p75 == p25`） | 不判 | 「基准没有离散度，比不出高低」 |
| 偏离中位数不到 10% | 不算偏离 | 「与基准持平（偏离不到 10%）」 |
| > P75 且偏离 ≥ 10%（变差方向） | 值得关注 | 「高于 P75（同类里最高的一档）」 |
| < P25 且偏离 ≥ 10%（变差方向） | 值得关注 | 「低于 P25（同类里最低的一档）」 |
| 其余 | 正常 | 「在 P25–P75 的正常区间里」 |

「变差方向」由指标自己的 `direction` 决定：耗时、卡关占比是 `higher_is_worse`，
高出一档才值得看；反过来 `higher_is_better` 的指标低出一档才值得看；
`neutral` 的（比如主动推进时长）一律不判。

对比时当前项目自己会被排除，不然是自己跟自己比。

## 6. 怎么用

```bash
# 存一次体检
python -m playpulse bench add data/projects/星屿开箱/试玩数据.csv --project 星屿开箱

# 看库里有什么
python -m playpulse bench list

# 看基准线本体（默认只显示 7 个核心指标，--all 显示全部）
python -m playpulse bench show

# 我 vs 同类
python -m playpulse bench compare data/raw/试玩数据-合成-100份.csv --project 开箱物语

# 出报告时顺手存档，报告里多一节「与基准线的对比」
python -m playpulse check <数据> --project 开箱物语 --note "第 2 轮内部试玩"
```

Web UI 的「📈 基准线」页有三个页签：基准库、基准线本体、我 vs 基准线，
最后一页有个存档按钮。

没有别的项目数据也想看效果？`python scripts/make_bench_demo.py`
会用现有合成数据派生三个难度曲线不同的项目（星屿开箱 16→39→59 秒、
机械迷城 15→37→54 秒、甜品消消乐 16→44→86 秒）。

## 7. 已知的局限（别拿去吹）

- **演示数据全是合成的**。界面上会明说「参与基准线的项目里有 N 个用的是合成数据」，
  这类记录只能验证链路，不能当真实基准。
- **3 个项目的分位数很脆**。P90 在 3 个点上基本就是最大值换个名字。
  真要用，建议先攒到 8–10 个项目再谈「基准」。
- **品类同质是硬伤**。如果接入的项目全是休闲开箱类，这个基准线只能叫
  「休闲开箱类基准」，不能叫「行业基准」——立项措辞见 01 第 18 章。
- **关卡序号对齐是有损的**。不同项目第 2 关的设计意图可能完全不同，
  序号对齐只是目前能拿到的最粗的可比维度。将来有了「关卡功能标签」
  （教学关 / 资源关 / 瓶颈关）应该按标签比。
