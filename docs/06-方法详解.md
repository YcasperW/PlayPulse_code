> 读法：**记住「功能」，不必记「def」**。本轮重构把「一个功能被拆成 3-4 个 def」的地方
> 合并成了一个 def，全项目 def 数从 **146 降到 105**，代码从 4298 行降到 4032 行。

## 命名规则（看到名字就知道干什么）

1. **动词开头 + 宾语跟上**：`split_quadrants`（算四象限）而不是 `quadrants`；
   `count_codes_by_level`（按关卡数编码）而不是 `_code_distribution`。
2. **返回布尔就加 `is_`**：`is_trustworthy`、`is_synthetic`——一眼看出是个判断。
3. **返回集合就说清是什么集合**：`computable_ids`（能算的指标 id 列表）、
   `blocked_with_reason`（算不了的指标 + 缺什么字段）。
4. **同名不同义必须拆开**：原来 `describe` 在两个模块里意思完全不同，
   现在是 `statsx.describe_sample`（描述一组样本）和 `schema.explain_field`（解释一个字段）。
5. **不再用缩写**：`_idx_table` → `_index_table`，`_fmt` → `fmt_num`。

| 字段提取 | `_referenced_fields` + `eval_formula_rows` | `eval_formula_rows` |

**没合的，以及为什么：**

1. **`@property` 合不了**——`Dataset.n_players`（被引 28 次）、`levels`（30 次）、`versions`（19 次）
   是"对象的字段"，不是功能步骤，合并等于把属性变回手算。
2. **11 张分析卡片合不了**——它们不是"一个功能的 11 个步骤"，而是"11 个不同问题"，
   并列挂在 `CARDS` 这张表上。记法是「一张表 + 表里有 11 行」，不是 11 个函数。
3. **5 张图同理**，是图表目录，不是步骤。
4. **递归函数合不了**——`_eval_node` 必须调用自己来走 AST。
5. **被多处调用的工具合不了**——`apply_scalar_or_series`（14 次）、`_esc`（10 次），
   内联等于把同一段代码抄十几遍。

## L0 契约与口径层

### 1. 字段字典查询 — `fields_of_layer` / `FieldSpec.explain_field`（schema.py）
按层（通用/品类/项目）取出该层的字段定义；`explain_field` 返回一个字段的单位、取值域、人话解释。
41 个规范字段是口径的地基：上游表头写"通关时长(s)"还是"用时/秒"，都翻成同一个 `duration_sec`。

### 2. 公式引用了哪些字段 — `MetricDef.required_fields`
从公式里扫标识符、排除函数名，得到这个指标依赖的字段。用来判断"这批数据算不算得出这个指标"。

### 3. 本体加载 — `Ontology.__init__` / `Ontology.load_from_yaml`
`__init__` 把 YAML 解析后的 dict 变成 `MetricDef / CompositeDef / RuleDef` 三个数据类。
**坑**：YAML 1.1 会把裸键 `on:` 解析成布尔 `True`，所以配置改写成 `target:`，解析时三种写法都兼容，缺了直接 raise。
`load_from_yaml` 读文件 + 顺带跑校验，让配置错误在启动阶段就炸，而不是跑报告时才炸。

### 4. 本体校验 — `Ontology.validate_formulas`
拿一组全 1.0 的假变量把每个公式跑一遍，语法错/引用了不存在的函数直接 raise；
复合指标还要检查 components 存在、权重和接近 1.0。返回警告列表（空 = 全通过）。

### 5. 本体查询 — `Ontology.metric` / `metrics_of_layer` / `computable_ids` / `blocked_with_reason`
按 id 取指标、按层取指标；`computable_ids` / `blocked_with_reason` 按数据实际有哪些字段判断能算哪些、
算不了哪些（后者要显式报出缺什么，不默默跳过）。

### 6. 口径导出 — `Ontology.to_markdown`
把整个本体导出成 Markdown 文档，**这是痛点①（口径不统一）的直接交付物**：需求评审贴这份，
策划和数据看同一份定义。`cli glossary` 就是调它。

### 7. 本体单例 — `default_ontology`
全局只解析一次 YAML，之后复用。避免每次提问都读文件。

### 8. 安全求值 — `safe_eval` / `_eval_node`
公式写在 YAML 里给别人改，就不能用 `eval`。`safe_eval` 用 `ast.parse(mode="eval")` 拿语法树，
`_eval_node` 递归走节点，只放行：数字常量、白名单变量、白名单函数、四则运算、比较、与或。
其余一律抛 `ExprError`。`check_formula` 是只校验不求值的版本，给加载阶段用。

### 9. 标量与整列的适配 — `apply_scalar_or_series`
校验阶段传进来的是标量（1.0），真实计算传进来的是整列 Series。没有这一层，
每个白名单函数都得写两遍。规则：全是标量 → 返回标量；有 Series → 广播后运算。

### 10. 白名单函数 — `safe_div` / `_zscore` / `_max_ratio` + `FUNCTIONS` 表
`safe_div` 让 0 分母返回 NaN 而不是 inf；`_zscore` 在标准差为 0 时返回全 0；
`_max_ratio` 归一化用"占最大值的百分比"而不是 min-max——**只有 3 关时 min-max 会把最轻的关压成 0**，
读起来像"这关毫无难度"，是误导。其余（abs/sqrt/log/round/min/max/clip/mean/median）是一行式，直接写在表里的。

## L1 数据接入层

### 11. 列名映射 — `map_raw_column`
去空格括号、认中英文别名，把乱七八糟的表头映射到规范字段；映射不上返回 None（不静默丢弃）。
新增一种表头 = 在 `schema.ALIASES` 加一行。

### 12. 数据容器 — `Dataset` 的 5 个属性
`n_rows`（行数）/ `n_players`（**玩家数**）/ `levels` / `versions` / `is_synthetic`。
**最关键的一条**：数据是 100 玩家 × 3 关 = 300 行，但样本量是 100 不是 300——
后面所有"够不够下结论"的判断都按 `n_players` 算，按行数会把显著性夸大三倍。

### 13. 切子版本 / 字段检查 / 覆盖率 — `subset_by_version` / `has_fields` / `field_coverage`
`subset_by_version` 切出某个版本；`has_fields` 判断某几个字段是否都有有效值；`field_coverage` 出各字段覆盖率（报告的「数据体检」章节）。

### 14. 读文件 — `read_file`
一个函数搞定两种形态：CSV 按 utf-8-sig / utf-8 / gbk / gb18030 顺序试探编码；
xlsx 按「现场填写表」解析（表头在中间，上方还有一对"标签行+值行"写玩家编号/水平/版本），
解析不了就退回普通表格读第一个 sheet。返回 (原始 DataFrame, 元信息字典)。

### 15. 规范化 — `to_fact_table`
七步：列名映射 → 元信息回填 → 类型强转 → 兜底字段（缺 player_id 用文件名、缺版本填 v0）
→ 派生字段（卡关占比/有效时长/时间膨胀能推就推）→ 数值区间体检 → 丢全空行。
每一步产生的问题都记进 `issues`，不静默处理。缺关卡列直接 raise（没它做不了任何关卡分析）。

### 16. 载入 — `load_auto`
唯一入口。文件单读，目录批量读；多文件合并后按「玩家+版本+关卡」去重（保留最后一条）。
单个文件读失败不中断，记一条 error 继续处理剩下的。

## L2 统计层

### 17. 数字格式化 — `fmt_num`
空值和 NaN 显示破折号，绝对值 ≥100 不带小数。避免出现"nan%"这种读不懂的东西。

### 18. 样本量判定 — `verdict_by_sample_size`
≥ 门槛（默认 8 人）→ 可下结论；门槛的一半以上 → 只给方向；再低 → 拒绝给判断。
**注意单位是玩家数。**

### 19. 单组描述 — `describe_sample`
点估计 + Bootstrap 百分位 95% 区间 + 诚实性判定 + 一句可直接放进报告的话。
用 percentile 而不是 BCa：BCa 更准但实现复杂、小样本上反而不稳，percentile 可解释可复现。
种子固定 20260922，重跑结果一致。

### 20. 两组对比 — `compare_two_groups`
一次性给出：两组点估计、差值、**差值的 Bootstrap 区间**、Cohen's d、Mann-Whitney p、一句诚实结论。
铁律只有一条：**差值区间完全落在 0 的一侧才算"超出噪声"**；跨过 0 就明说"差异可能只是噪声"。
用 d 和 Mann-Whitney 而不是 t 检验，因为试玩时长右偏，正态假设不成立。

### 21. 效应量翻译 — `explain_effect_size`
把 d 翻成人话（几乎无差异 / 小 / 中 / 大 + 变难还是变易）。p 值只回答"是不是巧合"，
d 才回答"差了多少"——而策划要的是后者。

## L3 计算层

### 22. 结果容器 — `LevelMetrics.value_at` / `detail_at`
`value_at` 取某个指标在某关的点估计；`detail_at` 一次给出点估计 + 区间 + 样本量 + 判定。

### 23. 行级求值 — `eval_formula_rows`
在一张表上求值一个指标公式，返回行级 Series；公式里引用到但表里没有的字段按全空处理
（后面会被计为"算不了"，而不是悄悄填 0）。

### 24. 关卡指标计算 — `compute_level_metrics`
四步走完，顺序不能变：
1. 字段够不够 → 不够就记进 `skipped`；
2. 行级求值（300 行 → 300 个值）；
3. **聚合到（玩家 × 关卡）**——同一个玩家在同一关可能有多条记录（重开），
   这些不是独立样本，先合成一格，此时样本量才等于玩家数；
4. 对"每位玩家一个值"做 Bootstrap。
第 3 步是置信区间不假性收窄的关键。

### 25. 复合指标 — `compute_composites`
难度指数 = 耗时 0.35 + 卡关占比 0.30 + 尝试次数 0.20 + 挫败感 0.15，各分量先按占最大值百分比归一再加权。
感知难度曲线是逐关累加（首关强制 0 起点，因为这条曲线看的是形状不是绝对值）。
**复合指标不给置信区间**（置 NaN）——宁可不给假区间。n 与档位沿用权重最大的那个分量。

### 26. 四象限 — `split_quadrants`
按客观难度与感知难度的**中位数**切分（关卡少时比均值稳健），把每关分进四个象限：
真实卡点 / 假性难度 / 顺滑但可能无聊 / 心流无感消耗；再算客观排名与感知排名的背离度。

### 27. 玩家 × 关卡矩阵 — `player_level_matrix`
返回 (玩家 × 关卡) 的指标矩阵。**后续所有统计必须基于这个矩阵，不能直接基于原始行**，
否则同一个玩家被当成多个独立样本。

## L4 诊断层

### 28. 一条发现 — `Finding.is_trustworthy` / `to_row`
`is_trustworthy` = 样本量是否够格下结论；`to_row` 摊平成报告表格的一行。
刻意把 conclusion（结论）和 advice（建议）分开——通用 BI 只给前者，策划要的是后者。

### 29. 体检结果容器 — `PulseCheck.findings_by_severity` / `findings_sorted` / `findings_as_table`
按严重度筛选、按「先严重度后关卡」排序、转 DataFrame。

### 30. 跑一次体检 — `run_pulse_check`
算指标 → 算复合 → 依次跑四类规则检测 → 出归因分布、选择分布、曲线形状。
规则不在代码里，在 `metrics.yaml` 的 `rules:` 里，改阈值不用改代码。

### 31. 跳变检测 — `detect_difficulty_jump`
相邻关卡比值超过阈值就报：耗时 >1.5 倍是**断崖**，尝试次数 >1.8 倍是**硬卡点**。

### 32. 阈值检测 — `detect_threshold_breach`
绝对值超阈就报：卡关占比、时间膨胀系数、「想退出」占比（>20% 即准流失）。
时间膨胀还有一个反向信号：所有关都 <0.8 可能是**无决策的挂机消耗**，会额外给一条复核提示。

### 33. 感知背离 — `_detect_perception_gap`
客观排名与感知排名差超过阈值就报，附象限名与对应建议。
「假性难度」（数据不难但玩家觉得难）通常不是数值问题，改数值无效。

### 34. 曲线形状 — `describe_curve_shape`
判定曲线是锯齿上升（健康）/ 平缓上升 / 直线上升 / 平台期 / 不规则，并给出人话点评。

### 35. 曲线提示 — `detect_curve_problem`
形状不是锯齿上升时，给一条低优先级提示（附目标形状）。

### 36. 编码字段分布 — `count_codes_by_level`
统计卡关原因码、卡关选择码的分布（编码 0 = 没卡住，不计入），返回 (逐关, 整体)。
两个字段共用它，只是传的码表和列名不同。

### 37. 对比结果容器 — `VersionDiff.verdict_sentence`
一句话总评；没结论时明说"未检测到可靠差异"，而不是留空。

### 38. 表行构造 — `_diff_row`
把一次 compare_two_groups 的结果摊平成表格一行（旧值/新值/变化/差值区间/效应量/p/是否超出噪声/可信度）。

### 39. 版本对比 — `version_diff`
按关卡对齐两版，每关每指标算 Δ 中位数 + 差值区间 + d + p。三类警告：
样本不平衡、每组 <8 人、**两版是同一批玩家时的学习效应**（同一批人玩两次，第二版天然更快）。

### 40. 结论生成 — `_conclusion_lines`
第一句是总评（整体变难/变易/有得有失/未检测到差异），后面是支撑细节：
变化最大的指标、准流失信号的变化、以及"另有 N 项未超出噪声，不要当成真实改善汇报"。

### 41. 存档放哪 — `bench_root` / `project_dir`
根目录优先读环境变量 `PLAYBENCH_HOME`，没有就落到 `data/bench`。**一个项目一个目录**——
目录名就是项目名（`_slug` 会把文件系统不合法的字符换掉，中文保留）。
这个目录就是隔离边界：删掉一个目录，那个项目在基准库里就彻底消失。

### 42. 一次存档是什么 — `RunRecord`（`save_run` / `load_runs` / `list_projects` / `latest_run_per_project`）
存的是**体检的结论，不是体检的原料**：通用层各指标 × 各关卡的点估计、难度曲线、发现清单、玩家数、
是否合成数据、本体版本。**一行原始记录都不存**——这样别的团队才愿意把结果交上来。
`latest_run_per_project` 保证"一项目一票"：同一个项目交十次，也只按最新一次计入基准线。

### 43. 基准线怎么算 — `build_baseline` / `Baseline.row_at` / `Baseline.is_trustworthy`
按（指标 × 关卡）把一个一个小格子跨项目拉出来，算 P10/P25/P50/P75/P90，
同时记下这一格有几个项目撑着、够不够门槛（`MIN_PROJECTS = 3`）。
不够就说"基准不可信"，报告里照实写"现在还不能说你在同类里排什么位置"。

### 44. 一格一格地判 — `judge_against_baseline`
拿本次的点估计去撞基准线，判三件事：位置（高于 P75 / 低于 P25 / 中间）、偏离多少百分比、
这个方向是不是"变差"（`_metric_direction`：卡关率越高越差，通关率越高越好）。
两个刻意不说高低的例外：**基准没有离散度**（各项目取值一样，`p25 == p75`，比不出高低）；
**偏离不到 10%**（`MIN_DEVIATION_PCT`）一律算"与基准持平"，避免把噪声说成结论。

### 45. 整份对比与结论 — `compare_to_baseline` / `_compare_conclusions` / `BenchCompare.verdict_sentence` / `baseline_table_for_display`
`compare_to_baseline` 是入口：先把**自己排除**（`exclude=project`，不然拿自己比自己），
只取通用层指标（品类层跨项目比没有意义），默认只比 7 个核心指标，
再拼出对比表、告警（合成数据 / 项目数不够）、以及按偏离幅度排序的结论句。
`baseline_table_for_display` 负责给表补中文列、把 `True/False` 换成"是/否"——
布尔值直接进表格在报告里会显示成 `True`，很难看。

## L5 呈现层

### 46. 图表基础 — `setup_chinese_font` / `fig_to_base64`
处理中文字体（否则图里全是方框），把图转成 base64 以便 HTML 单文件自包含。

### 47. 五张图

| 函数 | 画什么 |
|---|---|
| `fig_difficulty_curve` | 难度曲线，阴影是 95% 区间，红点是断崖 |
| `fig_quadrants` | 客观 × 感知四象限散点 |
| `fig_distribution` | 归因 / 选择的占比条形图 |
| `fig_version_diff` | 两版难度曲线叠图 |
| `fig_metric_bars` | 指标柱状对比 |

### 48. 报告落盘 — `Report.save_files`
一份报告同时存 md 和 html 两个文件。

### 49. 报告编排 — `build_report`
往 `sections` 里堆块（块是 `H/P/CALLOUT/TABLE/IMG/LIST/RAW` 七个一行式构造器），
再由两个渲染器各自渲染。**不这么做迟早写成两套逻辑**，然后出现"MD 里 n=8、HTML 里 n=10"。
章节标题的中文序号由 `_sec` + `_CN_NUM` 计数器生成，不是硬编码的——
所以传了 `bench=` 参数、中途插入「与基准线的对比」一节时，后面的编号自动顺延，不用手改一遍。
十二个章节：概览 → 一句话结论 → 曲线 → 关键发现 → 逐关明细 → 四象限 → 归因 → 选择
→ 版本对比 → **（有基准线时）与基准线的对比** → 行动清单 → 可信边界 → 数据体检 → 口径说明。

### 50. 一句话总评 — `_headline_verdict`
没有问题时也要说清楚，不能留空（"未检测到异常"后面必须跟"也可能是样本量不够"）。

### 51-53. 三张内容表 — `_level_detail_table` / `_honesty_table` / `_glossary_table`
逐关逐指标明细（**数值与量纲分列**——unit 里混了真单位和取值域，`1-5` 跟在数字后会拼成 `1.191-5`）；
各指标样本量 vs 门槛；本次用到指标的口径。

### 54. 行动清单 — `_action_items`
把 findings 转成可执行动作（带位置和"样本 N 人，先验证再动手"的后缀），并去重。

### 55. Markdown 渲染 — `render_markdown`
表格手写，不依赖 tabulate。

### 56. HTML 渲染 — `render_html`
同一份 sections 渲染成单文件自包含 HTML（图 base64 内联），能直接发给策划离线打开。

## L6 交互层

### 57. 卡片结果 — `CardResult.render_text`
拼成纯文本供 CLI 打印。

### 58. 意图打分 — `Card.keyword_score`
关键词命中打分，长词权重更高。**只做路由，不做语义理解**——路由错了最多答非所问（用户一眼能看出来），
生成 SQL 错了是"答得很有道理但口径是错的"（看不出来）。

### 59. 结论后缀 — `_verdict_suffix`
样本不足时在结论后面加"（样本 N 人，仅作方向参考，别据此改数值）"。

### 60. 难度指数表 — `_index_table`
各关难度指数，按指数降序（"哪关最难"和"哪关最顺"共用它，后者反序取）。

### 61. 十一张卡片

| 函数 | 回答什么问题 | 口径要点 |
|---|---|---|
| `_card_hardest_level` | 哪关最难 | 按难度指数，**不是按耗时** |
| `_card_easiest_level` | 哪关最顺 | 指数过低要确认是"设计得好"还是"没内容" |
| `_card_curve` | 曲线长什么样 | 附逐关相对上一关的倍率 |
| `_card_playtime` | 一次通关要多久 | 各关中位数相加，不是总时长中位数 |
| `_card_stuck_reason` | 为什么会卡住 | "不知道要干嘛"是信息问题，改引导别改数值 |
| `_card_stuck_choice` | 卡住时选什么 | 退出占比 >20% 即准流失点 |
| `_card_segment` | 新手老手差多少 | 分层后样本腰斩，可信度逐组重判 |
| `_card_drop_risk` | 哪关在赶人 | 汇总断崖/硬卡点/准流失 |
| `_card_perception` | 觉得难还是真的难 | 四象限识别假性难度 |
| `_card_trust` | 这个结论我能信吗 | 样本量单位、可信结论数、合成数据标记 |
| `_card_glossary` | 指标怎么算的 | 口径单一来源 |

### 62. 路由 — `route_intent`
必须 `key=lambda x: x[0]`，否则并列时会去比 Card 对象而抛 TypeError。

### 63. 兜底 — `fallback_card`
刻意不做"我帮你猜一个"。列出当前能回答的问题，并告诉用户怎么加一张新卡（先定口径再配卡）。

### 64. 问答入口 — `ask`
路由 → 跑卡片 → 卡片跑挂了也要说实话（通常是缺字段，指向报告的「数据体检」章节）。

### 65. CLI — `_print_issues` / `cmd_check` / `cmd_diff` / `cmd_ask` / `cmd_glossary` / `cmd_bench_*` / `build_parser` / `main`
四个主命令：体检出报告、版本对比、追问、导出口径文档。
`cmd_check` 多了 `--project/--note`：给了项目名就把这次体检存档，
**并且先比再存**（顺序反了就会拿自己跟自己比，得出"你和基准完全一致"的废话结论）。
`bench` 是二级子命令：`add` 存档、`list` 列项目、`show` 看某项目的基准分位、`compare` 比对、`help` 讲规矩。

### 66. Web UI — `ui_common.py` + `app.py` + `pages/`
从单页六 Tab 改成**多页**：`app.py` 是首页（Hero + KPI + 报告 / 发现 / 逐关三个 Tab），
`pages/` 下四个页面（版本对比 / 基准线 PlayBench / 口径说明 / 追问），
公共能力全收在 `ui_common.py`（样式、上传落盘、侧边栏数据源、三级缓存、发现卡片渲染）。
两个实现上的坑：
跨页只能传**路径字符串**，不能传 `UploadedFile` 对象（离开上传页对象就失效）；
首页是**上传即出报告**，没有"开始分析"按钮，靠 `(路径, 项目名, 版本对)` 这个签名判断要不要重算。

### 67. Excel 导出 — `export_excel.py`（2026-11-06 加）

第三个渲染器，读的还是 `build_report` 产出的同一份 `sections`，不另算指标。
`excel_bytes` 出字节给 Streamlit 下载按钮，`save_excel` 落盘给 CLI。
布局：文字 / 提示 / 清单按原顺序铺在「报告说明」，每个 `TABLE` 块拆成独立 sheet
（表头带自动筛选、冻结前两行）；sheet 名由 caption 去掉「表 N」前缀生成，
避开 Excel 的非法字符与 31 字上限，重名自动加序号。图片不进 Excel，留一行说明指向 HTML 版。
`_clean` 把 NaN / numpy 标量 / 以 `=` 开头的字符串处理成能安全写入的值；
`_width` 中文按两格算列宽；`_fit` 统一收列宽上限 60。

报告里的「数值」列是带单位的字符串，在 Excel 里不能直接算。所以 `build_report` 把
`level_metrics.wide` 换成中文列名塞进 `meta["wide"]`，Excel 里多出一张
「原始指标（可计算）」，全是原生 int/float。`Report.save_files` 默认出 xlsx，CLI 用 `--no-excel` 关掉。

## 一句话串起来

**契约层定规矩 → 接入层收数据 → 计算层出带区间的数 → 统计层盖章定可信度
→ 诊断层照表判读 → 基准线告诉你这在同类里算什么水平 → 呈现层写成人和机器都能读的报告
→ 交互层让人能追问。**

改指标/阈值只动 `metrics.yaml`；加字段动 `schema.py`；加问法动 `cards.py` 加一行卡片；
调"多少项目才给基准线""偏离多少算异常"只动 `bench.py` 顶部两个常量。
