## 1. 一句话定位

**不是"游戏版 SQLBot"，而是"会主动出题的游戏测试分析师"—— 上传测试 CSV，不等你提问，先给你一份难度体检报告。**

## 2. 前置事实核查：为什么不能重复 SQLBot

### SQLBot 已覆盖的能力（2026-09 核实）
| 能力 | 状态 |
|---|---|
| LLM + RAG 的 Text-to-SQL | 已做，高质量 |
| 对话式问数、多轮对话 | 已做 |
| 可视化图表生成与切换 | 已做 |
| 深度探索（分析 / 解释 / 验证 / 预测） | 已做 |
| 数据看板搭建 | 已做 |
| 自定义提示词、术语库、SQL 示例校准 | 已做（"越问越准"） |
| 嵌入式集成（Web / 弹窗 / MCP，接入 Dify、n8n、MaxKB） | 已做 |
| 工作空间隔离 + 行列级权限 | 已做 |

**生态数据**：2025-08-07 发布，3000+ GitHub Star，12 万+ 次部署，GPL 协议（二次开发需保留版权、商用需单独授权）。

### Quick BI 智能小Q 透露的行业方向
| 能力 | 说明 |
|---|---|
| 智能问数 | 自然语言即问即答，取数过程可验证 |
| **波动归因** | 多周期指标波动对比，多视角拆解贡献度 |
| **异常自动下钻** | 自动识别异常，并拆解到细分对象定位根因 |
| 智能解读 / 智能报告 | 一键生成图文报告，可编辑可订阅 |
| 完整链路 | 数据获取 → 分析结论 → 策略输出 → 报告撰写 |

**行业共识**：问数本身已经不是价值，**从数据到决策才是**。

### 结论
Text-to-SQL 是 commodity，不是壁垒。重复造 = 零价值 + 工作室不会立项。

## 3. 核心机会：通用 BI 的一个错误假设

> **所有通用 ChatBI 都假设"用户知道自己该问什么"。**

对游戏策划，这个假设完全不成立：
- 策划不知道哪些指标重要（多数人只想得到"通关时间"）
- 策划不知道什么算异常
- 给他一个空对话框，他只会问"平均游玩时间是多少"

**这个假设的漏洞，就是本项目的立身之本。**

| 层 | 内容 | 归属 |
|---|---|---|

## 5. 五大特色

### 特色一：报告先行，问答兜底（反转交互范式）

| | 通用 ChatBI | PlayPulse（把脉） |
|---|---|---|
| 打开后看到 | 空对话框 | 一份已生成的《难度体检报告》 |
| 用户动作 | 自己想问题 | 从报告结论追问 |
| 前提假设 | 用户知道该问什么 | 用户不知道，所以我先说 |

体检报告自动包含：
1. 难度曲线与断崖点（跳变 > 1.5 倍的关卡）
2. 时间膨胀异常关卡（预估/实际 > 1.3）
3. 客观难度 vs 感知难度不一致的关卡（四象限偏离点）
4. 卡关归因分布（五类占比）
5. 样本量警告（n 不足时标注结论不可靠）

> 关键差异：Quick BI 也做异常检测，但它是**通用统计离群点**；本项目知道**在游戏测试语境下什么算异常**——这是领域知识的壁垒，不是算法的壁垒。

### 特色二：领域语义层（最扎实的技术壁垒）

SQLBot 的"术语库"是**空壳，要用户自己配**。本项目做的是**预置 + 可版本化**的指标本体：

| 策划说 | 通用 BI 翻译成 | 本项目翻译成 |
|---|---|---|
| "哪关最难" | `ORDER BY 耗时 DESC` | 难度指数 = f(耗时, 尝试次数, 卡关时长占比, 感知分) 加权 |
| "卡关" | 无对应概念 | 卡关时长 / 关卡时长 > 阈值 |
| "断崖" | 无对应概念 | 相邻关卡跳变比 > 1.5 |
| "这关干等太久" | 无对应概念 | 时间膨胀系数 > 1.3 |
| "改完变简单了吗" | 查两次自己比 | 版本对比 Diff（特色三） |

**再进一步**：指标口径用 `metrics.yaml` 之类的 DSL 定义，可版本化、可导出、可跨项目复用。
这实质上是**游戏测试领域的 dbt Semantic Layer**——行业内还没有人做。

### 特色三：版本对比作为一等公民

策划最高频、通用 BI 做得最差的场景：**改了数值，新版本到底变好还是变差了？**

- 不是"查两次自己比"，而是一句"v1.2 vs v1.3 难度对比"
- 自动输出：哪些关卡变难/变易、难度曲线形状变化、差异是否超过噪声
- 通用 BI 做不了，因为它不知道要"按关卡对齐、算差值、判显著性"

### 特色四：小样本诚实性（Statistical Honesty）

**最能建立信任、也最容易被写进 README 的特性。**

- 问题：通用 BI 在 n=8 的数据上照样画漂亮图、照样说"显著提升 12%"——**这是有害的**
- 本项目内置：
  - 样本量门槛，不足时**明确拒绝给结论**
  - 一律展示置信区间，不展示裸均值
  - 用 Bootstrap / 效应量（Cohen's d）而非均值差
  - 输出中显式标注"此结论基于 8 人样本，仅供方向参考"

> 这是道德高地：**通用工具在小样本上会骗人，本项目不骗人。**
> 对内部测试场景是刚需（10 个同事的数据本来就是小样本）。

### 特色五：结论 → 建议 → 可导出

跟随 Quick BI "数据 → 结论 → 策略 → 报告"的链路，但更垂直：

- 不只说"第 7 关跳变 1.8 倍"
- 而是说"建议：第 7 关资源产出 +20%，或在第 6 关增加一个宝箱位"
- 输出物直接是**能贴进需求文档的东西**（Markdown / 图片 / 结论卡片）
- 每次分析沉淀为可复用的**分析模板**，下次测试一键套用

## 6. 数据模型（别只做"游玩时间"）

**风险提醒**：如果数据只有"不同人的游玩时间"，产品会退化成一个玩具 Demo。
必须设计成可扩展的 playtest 数据模型：

- **事实表 `level_attempt`**：每次关卡尝试一行（玩家 ID、关卡 ID、版本、批次、耗时、主动时长、卡关时长、尝试序号、开箱数、资源缺口、是否通关）
- **事实表 `session`**：每次游玩会话一行（玩家、起止时间、到达关卡、自然停止点、总时长）
- **维度表**：`player`（是否策划、是否新手）、`level`、`build_version`、`test_batch`
- **主观评分表**：每关打完的感知分、挫败感、挑战感、预估耗时

有了这个模型，"时间膨胀系数""断崖""版本对比"才能算，产品才是分析系统而非查询 Demo。

## 7. 技术路径建议：不要从头造

**推荐路径**：SQLBot 作为查询层，本项目只做上三层。

```
CSV/Excel 上传
  → 数据规范化（自建，轻）
  → 语义层：指标本体 + 口径 DSL（自建，核心）
  → 洞察层：断崖/不一致/版本对比检测（自建，核心）
  → 查询层：SQLBot API / MCP（复用，不造）
  → 输出层：报告生成（自建）
```

好处：
- MVP 速度快 5–10 倍，不用碰 Text-to-SQL 的坑
- 叙事清晰："我们不是另一个 Text-to-SQL，我们是它上面的领域大脑"
- 注意 SQLBot 是 GPL 协议，若涉及商用需评估授权；也可替换为自研轻量 SQL 生成或直接写死指标 SQL

**关键判断**：既然指标本体是预定义的，**根本上不需要通用 Text-to-SQL**。
绝大多数分析可以落成预置的分析卡片 + 参数化查询，LLM 只负责选卡片、填参数和解读结论。
这反而更准、更快、更可控——**"不生成 SQL" 可能才是本项目最对的技术决策。**

## 8. MVP 范围

### 做（3 件事，别的都不做）
1. CSV 上传 → 自动识别列语义 → 规范化入库
2. 一键生成《难度体检报告》（断崖 + 时间膨胀 + 四象限 + 样本量警告）
3. 版本对比 Diff

### 明确不做
- 通用自然语言问数（交给 SQLBot）
- 图表类型切换、美化、仪表板搭建（商品化能力，无差异）
- 多数据源连接、权限体系、企业级功能
- 预测类功能（小样本上做预测 = 胡说，与特色四自相矛盾）

## 9. 工作室立项论证

### 内部 ROI
- 工作室**每个项目都要做测试分析**，且流程高度重复 → 一次建设、多次复用
- 把"某个策划脑子里的方法论"变成**工具**，人走了方法论还在
- 缩短从"测完"到"知道该改哪"的时间

### 外部价值
- 开源领域空白：Text-to-SQL 工具一堆，**游戏测试领域的分析 Agent 几乎没有**
- 目标用户明确：中小游戏团队、独立开发者（请不起数据分析师，也不会用 Metabase）
- 天然的技术品牌素材：可写成文章《为什么通用 ChatBI 在游戏测试上会骗你》

### 壁垒在哪（要诚实）
- **不是技术壁垒**：Text-to-SQL、图表、Agent 编排全是 commodity
- **是知识与数据壁垒**：领域指标本体 + 分析范式 + 真实测试数据的持续积累
- 这意味着：**先发优势重要，且需要真实数据喂养**
- 【2026-09-18 更新】通用性风险已大幅缓解：工作室 20+ 项目可覆盖，本人手上 4 个可立即试验 →
  但立项论据要从"通用"改为"**跨项目基准线**"，架构上需支持三层指标本体，详见第 14–18 章

### 立项时要能回答的三个问题
1. 为什么不用 SQLBot 现成的术语库配一下？（答：被动问答、无领域指标模型、配置不可复用不可版本化、小样本会胡说、GPL 商用受限）
2. 只有一款游戏的数据，怎么证明通用？（答：这是最大风险，见下）
3. 做出来谁用？（答：先内部自用跑通，再开源）

## 10. 风险（诚实版）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 退化为"SQLBot 简化版" | 最大风险，一旦发生项目就废了 | 立项时就锁定"不碰通用问数" |
| 数据单一 | 现在只有一个游戏的一类数据 | 至少接入 2–3 个不同游戏/玩法验证通用性 |
| 小样本 → 结论不可信 → 工具本身被质疑 | 与特色四同源 | 把"诚实性"做成卖点而非遮掩 |
| 工作室内部需求不刚性 | 大家习惯用 Excel 了 | MVP 先证明能省下"从数据到结论"的时间 |
| GPL 协议风险 | 若基于 SQLBot 二次开发且商用 | 优先走 API/MCP 调用而非改源码；或自研查询层 |

### 12.0 命名四原则（先立标准，再挑名字）

| 原则 | 说明 | 反例 |

### 12.1 候选对比

| 候选 | 中文名 | 核心意象 | 契合点 | 风险 / 短板 |

### 12.2 推荐定名

> **PlayPulse · 把脉**
> Take your game's pulse. —— 给游戏把个脉。

采用**主名宽、模块名准**的双名策略，避免主名被单一能力绑架：

| 层级 | 名称 | 说明 |
|---|---|---|
| 项目 / 仓库 | `PlayPulse`（把脉） | 对外统一品牌，GitHub 仓库名 |
| 核心功能① | **Pulse Check**（把脉体检） | 上传 CSV → 自动出难度体检报告 |
| 核心功能② | **PlayBench**（试玩基线） | 跨项目基准线，20+ 项目积累的核心资产 |

### 12.3 一句话 pitch（README 首行）

> PlayPulse 不是又一个问数工具。你上传一份试玩数据，它不等你提问，先告诉你哪几关在赶人、为什么赶人、该怎么改——以及在样本量不够时，它明确拒绝给你一个漂亮的假结论。

## 14. 最强论据：跨项目基准线（Benchmark）

### 14.1 不要只讲"复用"，要讲"别人做不到的"
"一个工具能给 20 个项目用" = 复用，说服力一般，评审会问"那他们为什么不用 Excel"。

**真正的杀伤力在于：20+ 项目的数据放在一起，能回答单个项目组永远回答不了的问题。**

| 层级 | 能回答的问题 |
|---|---|
| 单项目 | 我这游戏第几关流失最多？ |
| 工作室（本项目） | 我们工作室的休闲游戏，**一般**在第几关流失？ |
| 工作室（本项目） | 首日到达关卡的**中位数**是多少？新项目低于这个值就该预警 |
| 工作室（本项目） | 开箱类游戏的"健康卡关时长"区间在哪？ |

### 14.2 飞轮效应（立项的增长故事）
```
接入项目越多 → 基准线越准 → 对每个项目越有价值 → 越容易推动下一个接入
```
**这是"工作室项目"区别于"个人项目"的根本理由**，也是立项时唯一能让人眼睛一亮的故事。

## 15. 架构前提：三层指标本体

开宝箱的"卡关"和卡牌游戏的"卡关"不是一回事，所以指标本体必须分层：

| 层 | 内容 | 归属 |
|---|---|---|
| **通用层** | 会话时长 · 关卡进度 · 尝试次数 · 自然停止点 · 主观评分 | 平台预置，**强制统一口径** |
| **品类层** | 开箱类：开箱数 / 掉率体感｜卡牌类：回合数｜放置类：离线收益 | 可插拔品类包，随接入项目增长 |
| **项目层** | 各项目特有指标，用 DSL 自行扩展 | 项目组自配，不污染上层 |

**通用层强制统一是硬要求**——否则 20 个项目 20 套字段名，基准线永远算不出来。

## 16. 试点设计：4 个项目各验证一个假设

| 试点 | 选什么项目 | 验证什么假设 |
|---|---|---|
| P1 | 最能控的（开宝箱，数据自主设计） | 核心链路：CSV → 报告 → 结论是否真的有用 |
| P2 | 同品类、不同数值版本的项目 | 版本对比 Diff 是不是真刚需 |
| P3 | **不同品类**的项目（卡牌 / 放置 / 益智） | 语义层扩展性：新品类能否 1–2 天接入 |
| P4 | 已上线、有真实留存数据的项目 | 上线后指标链路（留存 / 付费）能否接住 |

> 4 个项目不是 4 次重复，而是 **4 个不同维度的证明**。评审很吃这个框架。

---

## 17. 新增风险（原第 10 章补充）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **"能覆盖"≠"会接入"** | 最大风险已从技术转为组织；每组都有自己用惯的 Excel | MVP 做成**只读不侵入**：导入现有表格即出报告；先做**列名映射**而非强制统一 |
| **品类同质** | 20+ 项目若全是休闲游戏，验证的是同品类复用，不是通用 | 定位诚实写"休闲游戏测试分析"，**不要宣称通用 BI**，一问就露馅 |
| **数据隔离** | 未上线项目数据敏感 | 项目级隔离是 **V1 必做项**，不是"以后补"，立项前提 |
| **口径统一是组织问题** | 强制统一既是价值也是阻力 | 先用映射层兼容，等对方看到基准线价值再谈统一 |

## 18. 立项措辞提醒

| 不要说 | 要说 |
|---|---|
| "能覆盖 20 多个项目" | "已确认可接入 X 个，我手上 4 个先跑" |
| "通用游戏数据分析平台" | "休闲游戏测试分析智能体" |
| "替代 Excel" | "导入现有 Excel 就能出报告，不改流程" |
| "AI 自动生成分析" | "主动给出难度体检报告，并标注样本量是否足够支撑结论" |

> 评审对"能""通用""替代"这类词过敏，对"已确认""具体数字""不改流程"这类词有好感。
