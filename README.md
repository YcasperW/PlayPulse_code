# PlayPulse · 把脉

游戏试玩数据的难度诊断与归因分析工具。面向未上线游戏的试玩阶段，提供一套可复现的自动化分析流程：使用者上传试玩数据后，系统无需交互提问即可生成诊断报告，定位难度陡增的关卡、分析卡关原因并给出调整建议；当样本量不足以支撑统计推断时，系统不给出确定性结论，而是标注该结论的可信边界。

项目并非通用问数 / ChatBI。全部指标集中定义于一份 YAML 语义层（14 项基础指标、6 条判定规则、2 个复合指标），因此不需要通用 Text-to-SQL；问答仅用于选取预定义分析卡片与解读结论。统计设计以小样本下的结论可信度为核心，报告中的具体数值与发现随每次上传的数据而变化。

> **数据说明**：仓库 `data/` 下的试玩数据，以及 `out/`、`site/` 中的样例报告，均为**合成 / 仿真数据**，用于验证分析链路，并非真实玩家记录。项目尚未上线，不存在线上效果数据。PlayBench 目前仅 1 个项目具备游戏数据，基准库内项目均为合成派生，不构成行业基准。

## 为什么值得做（三个人家做不到的点）

| 特色 | 通用 ChatBI / SQLBot | PlayPulse |
|---|---|---|
| 交互起点 | 等你提问 | **上传 CSV 直接出体检报告**，问答只做兜底 |
| 指标定义 | 术语库空壳，要你自己配 | **预置领域语义层**（知道"哪关最难"不是 `ORDER BY 耗时`） |
| 小样本表现 | 8 个人的数据上也说"显著提升 12%" | **n 不足时明确拒绝给结论**，只给置信区间 |
| 输出终点 | 图 + 表 | **结论 → 归因 → 建议 → 可导出** |
| 跨项目 | 各项目各算各的 | **跨项目基准线 PlayBench**（接入越多越准，自带飞轮） |

**关键技术判断**：指标本体是预定义的，所以**根本上不需要通用 Text-to-SQL**。LLM 只负责选分析卡片、填参数、解读结论。更准、更快、更可控，且彻底避开 SQLBot 的主场。

## 快速开始

```bash
pip install -r requirements.txt

# ① 上传即出报告（默认动作，不用你提问）
#    同时生成 out/ 下的 .md / .html / .xlsx；不想要 Excel 就加 --no-excel
python -m playpulse check data/raw/试玩数据-合成-100份.csv

# ② 版本对比
python -m playpulse diff  <数据> V1 V2

# ③ 追问一句人话（路由到预定义卡片，不生成 SQL）
python -m playpulse ask   <数据> "哪关最难？"
python -m playpulse ask   --list          # 看能问什么

# ④ 导出口径文档（给业务和数据对齐用）
python -m playpulse glossary -o 口径说明.md

# ⑤ PlayBench 跨项目基准线
python -m playpulse bench add <数据> --project 星屿开箱     # 存一次体检
python -m playpulse bench list                              # 库里有哪些项目
python -m playpulse bench show                              # 基准线本体
python -m playpulse bench compare <数据> --project 我的项目   # 我 vs 同类

# 出报告时顺手存档 + 附一节基准线对比
python -m playpulse check <数据> --project 我的项目

# Web UI（多页）
streamlit run app.py
```

> 上面命令里的 `data/raw/试玩数据-合成-100份.csv` 只是仓库自带的一份合成样例，
> 用于把流程跑通；换成自己的 CSV / Excel 即可。报告里的样本量、关卡结构与数值
> 都取决于每次上传的数据，样例规模不是系统要求。

想先看看基准线长什么样，但没有别的项目数据？跑一次
`python scripts/make_bench_demo.py`，它会用合成数据派生三个难度曲线不同的项目。

## 三大模块命名

| 模块 | 名称 | 作用 | 状态 |
|---|---|---|---|
| ① | **Pulse Check**（把脉体检） | 上传 CSV → 自动出难度体检报告 | ✅ |
| ② | **PlayBench**（试玩基线） | 跨项目基准线：按（指标 × 关卡）对齐同类项目，给出 P25–P75 分位位置 | ✅ 代码 |
| ③ | **Signal / Noise**（信噪比） | 小样本诚实性模块：n 不足时拒绝下结论 | ✅ |

PlayBench 的三条规矩见 `docs/07-PlayBench-跨项目基准线.md`，一句话版本：
**一个项目一票、只比通用层指标、项目数不到 3 个不给基准线。**

⚠️ ② 的 ✅ 只表示代码跑通了。手上 4 个项目里**只有 1 个有游戏数据**，
所以目前基准库里的项目全是合成派生数据，只能验证链路，不是真实行业基准。

主名宽、模块名准——避免被单一能力绑架。

## 三条铁律

1. **`chest_open` 必须带上下文参数**（当前关卡、累计次数、是否广告箱）。只埋一个"开箱次数"，后面所有分层分析都做不了。
2. **通用层指标口径必须强制统一**。否则 20 个项目 20 套字段名，基准线永远算不出来。
3. **MVP 只读不侵入**：能导入项目组现有的 Excel 就出报告，先做列名映射，不强制他们改流程。

## 立项时的措辞提醒

别说「能覆盖 20 多个项目」，也别说「4 个项目先跑」——真实情况是只有 1 个项目有游戏数据。
说「单项目已跑通，跨项目基准线的架构已就位、真实基准待数据」。
评审对「能」和「多」这两个字过敏。
